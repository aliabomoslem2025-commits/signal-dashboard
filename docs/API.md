# Local device authentication API

All routes are served by the customized Signal HTTP server under `/v1/local-auth`.

## Security model

- An administrator pre-authorizes a device with an E.164 phone number, Android ID, and an EC P-256 public key generated by Android Keystore.
- `POST /challenge` returns a short-lived random nonce only when the exact phone-number/device-ID binding exists and is enabled.
- The app signs the decoded nonce bytes with its non-exportable Android Keystore private key.
- `POST /verify` verifies the ECDSA signature and returns a six-digit compatibility code and a random registration-session ID over HTTPS.
- `POST /submit-code` verifies the code and marks the registration session as eligible for the Signal registration endpoint.
- The app then submits the verified session ID through the existing Signal registration API.

The six-digit code is returned only to the requesting client over TLS. It is not sent by SMS, voice, FCM, or another external channel. It is not an independent second factor; the cryptographic device signature is the actual device-possession proof.

## Client endpoints

### POST /challenge

Request:

    { "phoneNumber": "+491234567890", "androidId": "0123456789abcdef" }

Response:

    { "challengeId": "uuid", "nonce": "base64url", "expiresAt": 1790000000 }

The app decodes `nonce` with a Base64 URL decoder and signs the raw bytes with `SHA256withECDSA`.

### POST /verify

Request:

    { "challengeId": "uuid", "signature": "base64url-encoded-DER-signature" }

Response:

    { "code": "123456", "registrationSessionId": "base64url-random-session", "expiresInSeconds": 900 }

### POST /submit-code

Request:

    {
      "phoneNumber": "+491234567890",
      "registrationSessionId": "base64url-random-session",
      "code": "123456"
    }

Response:

    { "verified": true }

The server accepts at most five code attempts per registration session. Challenges and registration sessions are short-lived and stored in the dedicated local-auth table.

## Admin endpoints

Every admin request must have:

    Authorization: Bearer <LOCAL_AUTH_ADMIN_TOKEN>

- `GET /admin/devices?limit=50&q=...`
- `POST /admin/devices`
- `PUT /admin/devices/{phoneNumber}/{androidId}`
- `DELETE /admin/devices/{phoneNumber}/{androidId}`
- `GET /admin/events?limit=100`

Create-device body:

    {
      "phoneNumber": "+491234567890",
      "androidId": "0123456789abcdef",
      "displayName": "Office phone",
      "publicKey": "base64-encoded-X.509-EC-P-256-public-key"
    }

The browser dashboard never embeds the administrator token in static files. The administrator enters it at runtime, where it is kept for the active browser session.

## Dashboard deployment and browser origin

The dashboard Nginx container proxies `/v1/*` to `SIGNAL_SERVER_UPSTREAM`. Set the browser's Server URL to the dashboard's own HTTPS origin. This makes the API same-origin and avoids enabling permissive CORS on the Signal server.

## Required environment variables

- `LOCAL_AUTH_TABLE`: DynamoDB table name. Defaults to `signal_local_device_auth`.
- `LOCAL_AUTH_ADMIN_TOKEN`: high-entropy administrator bearer token. The admin API fails closed when unset.

Do not place either value in the APK, JavaScript bundle, or a public configuration file.
